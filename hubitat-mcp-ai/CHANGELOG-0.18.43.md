# HomeBrainOS v0.18.43 — Evidence-driven automation dependency inspection

## Motivation and verified limitation
The live 0.18.42 comprehensive audit established 272 scheduled queue entries; 48 app IDs decoded from carefully recognised scheduler keys; 47 identities matched in the installed automation list; and disabled *OwnTracks* and *Power saving: Livingroom Nest Mini* appear among the matching candidate IDs. **No scheduler row carried an explicit recognised owner field.** The IDs matched, but the prior report could not verify ownership, current rule dependencies or execution. Earlier independently supplied ClaudeAI observations about overlapping Bedroom 3 lighting and quiet failover heartbeat are leads, not verified configuration details from HomeBrain.

## General architecture
- Add an optional deterministic **read-only configuration investigation** to the comprehensive audit, after the previously collected scheduler and installed app ID indexes. Choose at most **six** real installed IDs: up to two disabled scheduler-key candidates, one candidate named for heartbeat/failover, and remaining lighting/lamp configuration candidates. IDs are never inferred from names or generated by the model; selection is constrained to the fresh installed inventory.
- Reuse the advertised `hub_read_apps_code` gateway with `hub_get_app_config({appId, includeSettings:false})`, maximum **two concurrent reads**, each capped at 2.5 seconds with a six-second shared budget. Do not retrieve Groovy code, raw settings, credentials or device commands. Return each attempt's exact ID, read outcome and elapsed time as read-only evidence.
- Validate `app.id` against the requested numeric ID and require a structured rendered configuration page before accepting content. A successful MCP request returning a wrong app or an error is not config verification.
- Derive **typed action-target device IDs** only from explicit `deviceId(s)`-type keys inside *action-scoped* structured config fields. A number in a paragraph, title, token or device label is not an ID. Only identical typed target IDs support a current-configuration shared-target observation, **not** a claim that both automations ran or conflicted.
- Identical action text may be surfaced separately as a **text-only possible overlap**, never authoritative shared-device identity. Generic trigger/action presence says current config contains a section, not what triggered historically.
- Preserve zero-model read-only System Check, Free default and existing confirmation controls. Missing gateway, elapsed budget, unparseable config, no candidates or incomplete action inputs leave evidence explicitly unverified.

## Confirmed gaps, to be investigated later
`hub_get_jobs` in this hub returns no explicit recognised app owner IDs. An app-key prefix and a current config page **do not** prove callback ownership, whether a disabled app is actually executing, or any physical/state outcome. A stronger callback-owner registry or dated execution logs would be necessary before declaring a disabled-app bug. Likewise, conclusive lighting redundancy requires independently verifying triggers and device action targets, ideally using full structured rule configuration or appropriately scoped Groovy source. This release does **not** invent these missing capabilities.

## Validation
Dedicated tests check exact candidate selection, positive typed edges, negative prose-only similarities, source validation, redaction of URL/secrets, two-read concurrency, strict read-only arguments, no-gateway and expired-budget cases, and integration into the current audit renderer. All three CI workflows must pass before merge; live Home Assistant verification is separate.
