# Hubitat MCP AI v0.18.357 — verifiable selected-device values, honest clock boundaries

## Source-grounded issue and fix
In the first user-rated useful v0.18.355 current-status answer (12.255s, four rounds and four tools), the model stated switch=off and power=0 W but the exported Technical JSON only summarized the two-candidate lookup fields and a heartbeat history. Claude's subsequent separate answer had more complete measured attributes and distinguished latest check-in from last switch/power change. The two responses were not source-identical, and the user liked HomeBrain's concise first answer.

The existing `homebrain_resolve_device` model-selected result already contains the verified selected target and its current values after resolving several candidates. Previously `ToolExecutor.result_details` retained no attribute values from that successful resolver return. `current_device_receipt_projection.py` now extracts an allowlisted, typed, privacy-bounded `reportedDeviceState` packet for the **exact source-backed resolved ID** from a direct device-ID read or one completed label-filter lookup. It does **not** accept model-invented IDs, ambiguous/unmatched resolutions, request-cache results, identity-fallback-only reads, or unchecked arbitrary attributes. It never persists private messages, IPs, URLs, app settings, credentials or arbitrary text.

This source packet is attached to the **existing** resolver's evidence receipt: **zero additional MCP calls and zero additional model rounds**. It contains only known state/health/power/current/energy and reporting-age/date fields when the source actually supplies valid scalar/enum values. No timestamp is manufactured for `power`, `switch` or any individual attribute: the receipt's `timestamp` is **host processing time**, `lastSeen` is a separately reported field, and `attributeChangeTimesVerified=false`. It is not proof of physical operation or live connectivity.

The existing `ground_current_device_status` guard can inspect the selected resolution state as well as the earlier exact-target lookup. If both receipts report overlapping values, they must agree; a mismatch fails closed instead of silently selecting a convenient reading. Other successful evidence reads still suppress that narrow single-device correction, preserving the original source authority boundaries.
