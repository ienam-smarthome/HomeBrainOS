# HomeBrainOS V2 alpha.126 — outcome-first causal source sufficiency

**Status:** candidate until exact-head GitHub Actions pass and merge. V2 ONLY. No V1, heating scheduler, native action, approval, or downstream device changes. The installed first-answer behaviour of alpha.126 is unmeasured.

## Source-real motivation (PRIVATE alpha.125 review, 16 November 2026)

An installed uncoached WHY question about a shared system starting earlier produced an emphatic, incorrect denial that the output had activated. The original in-request Technical JSON contains **eight successful read-only calls, zero failures, eleven model rounds, 626,950 provider-reported input tokens and ~49.4s server**. The model had retrieved a *focused inventory* containing multiple zone sensors plus the shared control output, but only queried HISTORICAL mode/setpoint/operating-state for two associated zone devices. It never queried the central output's event history or the scheduler's execution logs; a documentation/tool-guide read did not supply execution evidence. Its final claim that the shared output never turned on was unsupported by the inspected room-device histories. The separate owner-provided controller logs reported a pending demand, confirmed command and output heating report; those logs were **not read by the installed V2 request** and cannot be retroactively counted as successful original MCP receipts. Source-real human first-answer score **1/8** (grounding 1, completeness 0, causal calibration 0, usefulness 0). Device-independent result: success of a sibling sensor query does not verify absence of a historical output transition.

## New general engineering boundary

- **Outcome before cause.** The V2 read-only system skill, existing source-sufficiency model review and final tool-free factual audit distinguish the historical output/actuator's original switch/operating-state/command evidence from an input sensor's idle rows, the controller's current mode/setpoint, a location mode, current inventory and a documentation tool.
- New `causal_outcome_frontier.py` summarizes WHICH device IDs and exact attribute filters were queried through successful original read-only `hub_list_device_events` receipts. It separately enumerates bounded focused `hub_list_devices` inventory members and `hub_get_device` current-only subjects without event-history reads. It excludes location event lists from device history; large/broad inventory is never automatically enumerated or used to demand mass reads. It includes compact observed original state-value counts but explicitly cannot prove continuous observation, past absence, an internal cause or physical operation.
- Only for causal source review, when a focused inventory contains uninspected members or the candidate makes an apparent historical denial, the existing model review receives the concise **outcome-first checkpoint** and original-source scope index. **The model still decides** the actual controlled output, the offered READ-ONLY tool, the attribute, window, and whether any additional read is useful. It is not a device picker, a forced tool, a mandated query order or an extra model pass. Explicit no-new-read instructions, native action safety, approval and model-led route are preserved.
- The last final audit is instructed to correct categorical cross-device denials to a scoped UNKNOWN whenever the output itself was not historically inspected, not merely rewrite a confident falsehood into longer prose.
- PRIVATE Technical JSON adds `causal_outcome_source_frontier` navigation alongside the existing command-issuer/decision frontier. Original native MCP receipts remain unchanged. No house-specific IDs, code routes, controller patches or hidden actions.
