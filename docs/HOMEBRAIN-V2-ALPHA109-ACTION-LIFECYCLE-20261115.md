# HomeBrainOS V2 alpha.109 — completed native action lifecycle

**15 November 2026; V2 Preview only.** No private original household receipts, names, IDs, network identifiers, addresses or tokens are included.

## Observed installed defect

The owner's alpha.108 first-answer review confirmed a direct device imperative that stopped in a model-generated JSON native-tool **proposal**, followed by text saying approval would be offered. Eight paid model rounds and only read-only MCP receipts were present. No actual native write was selected for submission and no same-request UI approval was pending. The existing `action_selection` fallback stayed null, because its logic looked for specific confirmation phrases or a Python-style `hub_call_device_command(...)` string. The actual model output was a fenced JSON object. A successful text response (`success:true`) was misread as successful work. The device status was separately reported by a native read; absence of a new command is not proof of what occurred in a different time window, and state is not proof of the earlier initiator.

## General V2 correction

1. **Explicit terminal action lifecycle.** For a direct explicit device imperative in a web request, `inspect_action_lifecycle` classifies actual native writes using the original per-request call/receipt sequence and whether the actual MCP transport was entered. It never parses model prose or JSON. `not_prepared` means no selected native writer and no native submission; `native_write_not_submitted` means a writer was selected but never sent (e.g. declined/blocked, potentially uncertain); `native_accepted`, `native_rejected` and `native_result_unverified` distinguish original native response and unsupported downstream claims. A completed request has no live pending approval. The ordinary response `success` remains answer-status only, accompanied by explicit action lifecycle and `response_success_scope` metadata.
2. **No phantom approvals.** For a web request that ended without a model-selected native write, `action_selection` is **always** a safe `unprepared_confirmation` with `prepare_action`, `edit_request`, `dismiss`. These are NEW user-chosen request paths, not replay/approval of a model code block. The result answer explicitly says **No action queued**, no Approve card is currently present, and any further native action requires new evidence, actual tool selection and the original real approval card. This applies equally to silence, prose, JSON, markdown or fabricated command syntax. It does not depend on a brittle natural-language matcher. An attempted but declined/blocked write is NOT eligible for this easy retry path.
3. **Visible UI consistency.** The completed UI uses `action_lifecycle.status` and `action_selection.native_write_queued`, not answer `success` or model text, to show no-action cards and the action-specific status line. Accepted write receipts are labelled native acceptance only; a later physical transition is not inferred. During a live pending native write, the existing source-verified identity/ID/parameters gate still requires explicit same-request user approval. The app never executes commands from model prose, prints or old chat turns.
4. **Token-aware investigation guidance.** For imperative device actions, the model is advised to use focused native device filters and advertised command details before a verbose whole-home inventory. An already-satisfied observed state should be explained rather than silently reversed or acted upon. This guidance does not force controller/command selection, infer unobserved facts or impose an additional read/round.

## Synthetic regression and live gate

Synthetic cross-domain tests verify: a printed JSON code fence after an invoked bounded approval handoff yields **No action queued** and visible Prepare/Edit/Dismiss, zero native action submissions and zero pending native approval; final no-confirmation prose also gives the same fallback; an actual accepted native tool is never reclassified as unprepared; declined/contract-blocked selected commands cannot be silently requeued; native-success versus native-failure/unknown receipts remain distinct; read-only questions never show action choices; and a disabled web approval path never claims an approval card. Existing native prewrite, approval, evidence-scope, historical and V1 behaviour remains intact.

Update V2 Preview and test with an already-safe target or a low-risk genuinely desired action. Verify the exact original PRIVATE receipts, native UI pending approval when selected, no writes on Decline, and a proper fallback whenever the model stops at text. Check model reasoning/latency independently; synthetic CI alone does not prove the cloud model will select the correct writer.
