# HomeBrainOS V2 alpha.115 — original Ask approval for verified benign routine controls

**15 November 2026; V2 Preview only.** No private user device names, identifiers, credentials or raw household MCP receipts appear in this public note.

## Why

The owner approved eliminating the second **Approve** click for a fresh, fully verified ordinary light ON/OFF command. Alpha.114 had reduced a live test to ~7.4 seconds by source-first native discovery and one focused model writer selection, but still required a separate native confirmation card for ordinary light controls. The original new Ask now serves as explicit authorisation only for the bounded safe class; this MUST NOT become a blanket write-permission or apply to unrelated, high-impact or unverified operations. The existing upstream native MCP write permission and tool-schema checks remain authoritative.

## Exact scope and architecture

- The per-request V2 `Interaction.before_call` remains the sole native write confirmation gate, with `require_native_write_approval=True`. It gets an optional **single-use authorization proof** from the Agent only after: new conversation, no prior evidence; strictly one immediate literal ON/OFF; successful current-request original native inventory and detailed source; exactly one model-selected identical `hub_call_device_command`; no extra parameters or mismatched waitFor; original target/state/capability/advertised command validated by `routine_candidate`; and one focused AI writer round within a short current-source freshness window. The proof is matched against the actual native name and arguments again *inside* the confirmation gate. It is consumed by the very next native call and never replayed. Cancellation invalidates the proof. A write submission with unknown result is never automatically repeated.
- **Ordinary lights:** default-on Preview option `routine_auto_approve_lights`. The current original device detail MUST declare `Switch` and `Light` capabilities, exactly matching label, ID and commands, with opposite reported switch state. Disabled, virtual and mixed-purpose Light+Outlet surfaces are excluded, as are sensitive declared capabilities and obvious sensitive-purpose source names. Pure switch capability alone never grants auto approval.
- **Safe physical switches:** NOT presumed safe. `routine_auto_approve_safe_switch_ids` is an optional comma-separated, explicitly trusted native device-ID list. Candidate must still pass all routine exact-source requirements, deny sensitive capabilities/names and carry a physical Zigbee/Z-Wave/Matter inventory protocol. Network-control relays, virtual switches, heating/security/locks and automations never receive this exception just because a switch command exists. The empty default keeps all non-light switches approval-required.
- Any declared native `confirm` flag or automation persistence requirement ALWAYS wins: a separate approval card is shown regardless of eligible label/type. Other write operations, multiple commands, time-dependent requests, nonmatching IDs/arguments, rules, security devices, locks, heating and network blocking retain current confirmation. The model still selects native tool and arguments; the client does not generate a write from text.
- Only the actual original native accepted receipt may substantiate the terminal response. An in-command switch value or acceptance never proves independent later physical effect. PRIVATE Technical JSON now includes `routine_native_authorization.automatic_authorization_used` and `authorized_class`, not permission proof to reuse. The read-only /api/status reports whether light auto-approval is enabled and the count (not identifiers) of explicitly trusted safe switches.
- The Preview add-on defaults `routine_auto_approve_lights=true` for this explicitly requested behaviour, and can be turned OFF in add-on configuration. No V1 changes. No attempt to circumvent upstream/native master write permission or device allowlist.

## Acceptance and rollback

Synthetic tests use fictional read-only source responses and a scripted model. They assert that benign light Ask completes with one model tool-selection round and **no pending second card**, exactly one native write and original receipt-limited answer; default-disabled policy retains the real approval gate; an approved proof is single-use; changed device, command, extra parameters, native confirm, invalidated request, sensitive-source classes and untrusted switches fail closed. A correctly allowlisted benign mesh physical switch is eligible, but other generic switches require approval. The old V2 approval tests must remain green.

These tests cannot establish real Hubitat writes or prove physical outcomes or provider performance. Live acceptance: install V2 alpha.115, ask one new benign immediate light ON/OFF requiring a change, verify NO extra approval card, native accepted original receipt and source-limited response, model/tool timing and `routine_native_authorization` fields. Also test a deliberately sensitive (but DO NOT APPROVE) write and verify it still asks confirmation. If any non-benign/uncertain write is automatically authorised, revert alpha.115 and retain alpha.114.
