# HomeBrainOS V2 alpha.108 — native source → approval → answer

**15 November 2026. V2 Preview only.** Do not commit the owner's original private Hubitat receipts, device IDs, IP/MAC addresses, names, tokens or household telemetry.

## Installed source-real problem

The owner-supplied installed alpha.107 test completed a native deferred device action in ~24.7 seconds/seven model rounds, an improvement over the preceding 92.8 seconds/ten rounds. The action tool receipt reported `success: true`, an original native `*InMinutes` command, matching minute argument and a future timestamp in its **embedded write-result state**. A follow-up independent device state read and later physical/network effect were not established by the trace. The model's final answer changed the instruction from delayed onset **after N minutes** to a **for N minutes** restriction and guaranteed future automatic recovery without supporting receipts. The UI approval card displayed only the target's native ID because the preview was computed from write arguments alone, while `"5"`-style numeric strings were also hidden.

## Correction contract

1. **Original-source device identity.** `Interaction` now receives a tiny, display-only registry constructed from the original, successful, same-request `hub_get_device` receipts; the returned ID must exactly equal the requested source ID. The label is bounded plain text, and the original target ID remains visible. Failed/malformed/old conversation results and unnamed inventory snippets cannot supply a verified display label. Registration does not fetch additional native data, write to a device, change tool arguments, authorize a call or persist state across requests.
2. **Native command parameters.** The actual pending native parameters appear as numeric literals or safely validated numeric strings. The UI previews the exact original command name, retains original device ID, and distinguishes supported `InMinutes`/ `AfterMinutes` from `ForMinutes` only when the original source advertised that exact command. Changing a displayed input still disables approval and requires an edited new request; the display is never a writer payload.
3. **Output-only original receipt fidelity.** The verified action summary is generated only after the model-selected write actually executes, when a successful original current-request `hub_get_device` advertises the same exact target+command, the user's own request contains exactly one unambiguous numeric-minute period, native command suffix matches requested temporal semantics, submitted parameters match the requested integer and the *original native tool content* explicitly returns `success: true` with matching command/parameter. The output distinguishes `after N` delayed onset from `for N` duration and quotes parseable native pending timestamp fields strictly as **write-response state**, not independent readback. It never promises a future physical change, full block duration, or automatic restoration. If original source is insufficient or ambiguous, do not synthesize completion; if an executed known command contradicts the requested timing, publish a cautious discrepancy warning rather than a successful timer claim.
4. **Scope safety.** No additional model rounds, MCP reads, polling, provider tokens, inferred routers, native writes or UI approval bypass. Existing investigative and historical read-only answers are not replaced; only a verified narrow class of completed native minute commands is projected. The same native original receipts remain in PRIVATE Technical JSON for audit, with an additional `action_semantics_verification` status that does not itself prove a downstream physical result.

## Regression and acceptance

Fictional cross-device tests cover source-matched and wrong-ID labels, source failures, exact command advertisement, numeric string preview, real pending user approval and decline, a model falsely saying `for N` after an accepted `InMinutes` write, original-returned timestamp provenance, valid `ForMinutes` duration, contradictory operation semantic kind, missing native `success`, ambiguous time phrases and ensuring source data is not mutated. Synthetic end-to-end tests ensure one and only one model-selected native tool is submitted **after** an explicit UI approval. The library is not used to infer a specific private device ID or command.

For installed acceptance: upgrade V2 Preview to alpha.108; request one low-risk, genuinely desired operation, inspect before approval that the correct original source-returned label **and ID** are displayed with exact command/parameters, choose Approve or Dismiss, and compare the returned answer to PRIVATE original native MCP receipts. Require `after`/ `for` agreement and correct write-vs-readback vs future physical scope. No automatic live action or physical outcome is asserted from CI.
