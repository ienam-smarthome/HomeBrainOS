# HomeBrainOS V2 alpha.110 — fresh chats, cancellable pending work

**15 November 2026. V2 Preview only.** This note contains no real device identifiers, household information, account details, IP/MAC values or original private receipts.

## Live evidence and root cause

Owner-supplied installed alpha.109 first-answer trace shows ~299.4 seconds end-to-end, with ~214.9 seconds awaiting actual user native write approval and ~75.8 seconds spent in reported provider model rounds. The original MCP command was eventually submitted and accepted, followed by a separate device-status read, but downstream real-world behaviour was not independently measured. A UI screenshot of an earlier request showed >144 seconds waiting, without live source rows. The single `app.state.ask_lock` serialized all Ask operations, including a wait inside `Interaction.before_call()` for an approval choice; meanwhile `ui.html` disabled the Ask button, rejected Speak, and disallowed New chat whenever `activeRequest` existed. Thus a previous unanswered question or approval could block later unrelated commands, irrespective of the model's progress.

## General implementation (no device-specific command rules)

1. **Server-side request ownership.** Each normal Ask registers its current asyncio task alongside its request-scoped `Interaction`. `POST /api/activity/{request_id}/cancel` requires the existing authenticated web-UI header, invalidates the old pending approval **first** and cancels the task. The old task's `async with ask_lock` releases automatically on cancellation and its request/approval references are discarded. A late approval for the old UUID is rejected. The cancel route does **not** claim that an already-transmitted native write was reversed or guaranteed not to execute.
2. **Write boundary safety.** `Interaction` checks cancellation both before offering native approval and after user decision, and rejects late native writer submissions. The actual native transport entry is marked separately. When cancellation arrives after the native submission boundary, the API returns `native_write_outcome_unknown:true` even though the old Ask task is gone. Never retry or assume rollback on this ambiguous result. There is no write or target selection from UI prose, and a fresh request always requires its own real model-selected native tool and same-request approval.
3. **V1-style fresh Ask and Speak.** The Ask button stays enabled for any nonempty text even while another Ask is running; Speak may start and its transcript may submit as a new Ask. Every new user-initiated Ask/Speak creates a new UUID for `conversation_id`, sends `history:[]`, clears the previous conversation's ephemeral evidence and resets the old answer UI. A new question first verifies server cancellation of an active prior UUID; if cancellation fails, do not launch the second write. After the server confirms cancellation, the browser's old HTTP request is aborted; monotonically increasing request tokens and captured request IDs prevent stale callbacks/timers from overwriting the newer UI. The explicit New chat button is available even while an Ask is running, and a dedicated Cancel control stops an active request without starting another.
4. **Truthful progress.** The existing read-only `api/activity/{request_id}` status now includes the actual phase: queued for the global slot, reading the native catalog, awaiting the provider model round, in a native MCP call, or requiring native UI approval. The screenshot's old `Evidence · 0 calls` display is not confused with a claim that no model or device work occurred. Progress adds no model calls, native reads or periodic Hubitat polling; it reuses the existing UI activity-polling mechanism.

## Safety boundaries and tests

Synthetic FastAPI route tests use fictional devices and an approved HTTP client. They create an actual pending `before_call` gate, confirm the native writer has not run, cancel its UUID, prove a late approval is rejected and that a fresh independent Ask returns without waiting for the earlier 300-second deadline. A second test deliberately marks the native write submission boundary and confirms cancellation reports that the downstream outcome may be unknown. Read-only/manual cancel and missing-request behaviour are covered. Browser JS and real Chromium smoke tests exercise Ask, Speak and New chat with fresh conversation IDs, empty prior history, previous result isolation, and a cancellation transport. The user-facing Cancel control is a safety valve, **not a scheduled task manager**.

**Installed acceptance**: update V2 Preview only; submit a simple safe read-only Ask; before it finishes, submit another safe Ask or Speak. The later question should become current immediately after server cancellation, without carrying the old answer forward or exposing an old Approve button. If cancelling an in-flight native write, verify actual device state before performing any new write. Do not equate CI or an MCP success flag with physical effect. Performance comparisons should separate model rounds, human approval time and native tool latency.
