# HomeBrainOS v2 alpha.68 — evidence-bounded implementation feasibility

**Date:** 12 November 2026. **Scope:** general model-led explanation, tool/source selection and safe read-only follow-up. **Installed acceptance:** not yet performed. No real device, router, rule or automation changed.

## Observed problem

A private source-real alpha.67 first answer correctly identified a named physical target's separate network-control device and retrieved its full advertised native commands. No command represented the user's requested **delayed onset**, though immediate and temporary-duration actions existed. The response jumped from the supported finding "no direct delayed-onset command was advertised for this controller" to "a separate Rule Machine/Visual Rule can and must be created". It did not inspect a current rule-writer tool schema, a viable immediate/dated one-time trigger contract, delay/action model, permission grant, or persistence. A second review performed additional label/capability filtered inventory queries and claimed exhaustive controller coverage despite no supporting exhaustive search. These were source-completeness and implementation-feasibility defects, not evidence that the hub cannot ever support the workflow.

Prior V2 development notes flag Rule Machine one-time authoring and parent/trigger contract uncertainty. Such background notes are hypotheses and cannot substitute for THIS request's authoritative live writer/schema evidence.

## Changes

- Extend general action and automation skill guidance. A missing *direct* device command does not establish that another approach is *required*, *available*, *authorized* or *ready*. Separate a conceptual one-time delayed design from a working **presently exposed native authoring interface**, exact supported one-time/immediate/dated trigger, delay, target command and actual created schedule. A recurring rule or generic delay action cannot prove a one-time "start now then fire once" contract.
- Add a new **model-selected read-only `implementation_feasibility` source review** as an alternative use of the existing single evidence-sufficiency checkpoint when the model's own draft proposes creating/scheduling a rule, workflow or automation. This detects generic claimed implementation prose, not device names, user keywords, or incidents. Historical/causal questions and actual write outcome reviews retain their existing paths.
- In that review, ask the model to use available original successful MCP receipts, `homebrain_inspect_mcp_catalog` on the exact connected `tools/list` snapshot, and relevant existing read-only native `hub_get_tool_guide` / native app/rule/source reads. No tool or sequence is automatically chosen. A visible writer isn't proof of authorization or successful one-time authoring. A guide is generic descriptive data; it isn't a verified local trigger contract. A gateway candidate isn't a full leaf schema.
- The review retains the original, **read-only-only** catalog; no rule creation, device writes, alternative retry, permissions changes, or client scheduler. The extra text-only final claim audit does not run after this focused review, preserving the single source-check architecture and avoiding a known confidence regression.
- Scope search claims: `labelFilter` matches labels, not necessarily driver names; zero results in a filtered inventory or limited switch inventory don't establish all possible controllers were checked. Negative conclusions must be bounded to actual returned receipts. If feasibility remains unknown, the answer should say which exact contract remains unverified and frame the conceptual workflow conditionally.

## Fictional regression and limits

A synthetic valve device advertises only immediate `open`/`close`. A scripted model initially proposes a one-time timed rule. During the additional review, the model independently inspects the live schema of a *visible writer* via the existing local catalog inspector and reads a general upstream rule reference. The reference mentions delays and event triggers but does not substantiate a one-time immediate trigger. The scripted final answer correctly states that the design is possible in principle but this install's authoring contract/authorization is **not proven**.

Further scripted tests verify: missing writer produces scoped uncertainty rather than a global impossibility conclusion; the model cannot execute a rule writer during the review; a normal command-detail response creates no extra review; generic proposal language triggers the checkpoint without names of household devices.

These are *mechanism tests*, not independent live Hubitat evidence, a working automation creation test, or proof of Gemma's first-try answer quality. The implementation never alters V1 or the external Hub & Device Monitor.
