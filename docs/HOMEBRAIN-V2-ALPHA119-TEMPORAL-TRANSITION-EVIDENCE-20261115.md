# HomeBrainOS V2 alpha.119 — source-derived focal latest-transition chronology

**15 November 2026. V2 Preview only.** This engineering note does not disclose any real household device names, IDs, API keys or native receipts. All test fixtures are fictional.

## Source-real alpha.118 first-answer failure

In an uncoached read-only 12-hour heating question the model retrieved **six successful native read receipts** and spent approximately **103 seconds**, **10 model rounds**, **1,015,184 input tokens**, and **91.4 seconds model processing**. It named a last heating-to-idle transition for the requested TRV near **16:05**, but the inspectable filtered original TRV state history contained only later repeated idle reports, from about **17:00 to 22:00**. The wider TRV event responses were truncated in the returned model/Technical JSON view, so their intermediate rows could not be independently checked. The model had incorrectly transferred the main thermostat's recorded command and changes to the TRV. A fully inspectable original main-thermostat receipt also contained a **later heating at 21:53 and idle at 22:00**, yet the model kept discussing the earlier 15:58–16:05 cycle as the latest. A recorded scheduler command issuer on the main thermostat is not direct evidence of the TRV's transition or the scheduler's internal decision, and repeated idle rows cannot prove uninterrupted idle.

This case failed first-answer factual/causal grounding despite passing the alpha.118 failed-read recovery contract, because the tools *succeeded* but the available evidence was chronologically misinterpreted. More model reviews alone did not repair the source interpretation.

## V2-only general correction

- Add a **typed temporal evidence verifier** only for an explicit question of the form "when did [device] last change/transition from [state] to [state]". The supported typed states are ordinary switch, motion, contact and thermostat operating-state values. This is not a device label or household-specific patch; a target must resolve uniquely from **original successful current-request native inventory/device details**, and native event receipts must match that ID.
- Enumerate only **fully inspectable ORIGINAL native device-event rows**, preserve absolute offset-aware timestamps, event names, returned values and source receipt numbers; do not promote truncated client wrappers, partial prefixes, peer-device events, unrelated attributes, command rows, unparseable timestamps, or capped history into a focal transition. Requested relative hours must have a source-reported matching lookback/sinceTimestamp before declaring a pair within that period. A preceding observed state and a subsequent different observed state on the *same target and attribute* are necessary for an observed pair. Even a matching pair is only the latest **in the inspectable returned slice**; neither full retention nor the physical instant is independently verified.
- Expose a compact source-derived transition index during the **already existing** read-only model source review / causal follow-through, so the model can independently choose a useful discriminating read-only source if it exists. Do not assign a historian, query one automatically, create another model round or mandate a device. The compact index distinguishes the focal device from later events returned for another device. Retain reporter/recorded-command-issuer separation.
- At final publication, a narrow **output-only typed source contract** protects this exact latest-transition question from publishing an unsupported precise time or definite causal claim, even if repeated model-only reviews are overconfident. It publishes limited real focal before/after observations if present, otherwise a clear inability to verify the focal transition plus bounded positively verified peer context and unknowns. This follows the established explicit returned-event ledger pattern without altering the model's selected native tools or action authority.
- Skip the redundant **tool-free final claim audit** for this narrow question because its final wording is already source-derived; retain the model's normal first source review and opportunity for additional read-only tools. This should reduce wasted inference without imposing an arbitrary time cutoff on a genuinely useful investigation. All other question types keep their existing reasoning/audit flow.
- Preserve V1, the alpha.116/117 verified routine native control + postwrite readback, original Ask authority and sensitive approval requirements, historical-source retrieval policy and Hub & Device Monitor optionality.

## Acceptance boundaries

Synthetic tests use fictional device IDs and returned native receipts shaped like the live failure: a verified target with idle-only filtered event reports, a truncated unfiltered response, and a distinct thermostat with an earlier and later heating/idle cycle and a scheduler-issued command. They assert no fabricated focal transition, explicit later peer chronology, no device-to-device causal transfer, a source-verified most-recent observed focal pair when present, time-window limits, offset-aware timestamps, row-cap/truncation caveats and no intrusion into unrelated status/control questions. A scripted first-answer integration tests the existing model-led review and source-derived publication without an extra audit round or native writes.

**Not proved by CI:** that a newly available historian actually has the missing TRV transitions, that the app scheduler's execution logs prove an internal decision, live 12-hour completeness, factual-grounding pass rate, or alpha.119's installed latency. More sophisticated transition/causality extraction is valuable, but must be based on full original source provenance rather than invented timestamps. Roll back if a typed source transition output claims a physical event or changes the normal native write/approval path.
